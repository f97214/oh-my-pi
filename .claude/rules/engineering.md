# 實作期工程紀律

六節各自帶適用條件，不適用時整節跳過，不要為了套用而硬湊。

## 1. 非瑣碎決策的對抗審查

### 何時適用

滿足以下**任一**條件時，決策不得直接落地：

- 引入或修改分支邏輯
- 跨越模組或服務邊界
- 宣稱型別系統無法驗證的性質（執行緒安全、冪等、順序保證）
- 正確性依賴未來讀者看不到的脈絡
- 影響範圍不可逆（正式部署、資料遷移、對外介面變更）

**不適用**：機械性操作（改名、格式化）、單行且正確性顯而易見的修改、純工具設定、使用者已明確指示的做法。

### 程序

1. **寫下 CLAIM** — 兩到三行講清楚「決定了什麼、為什麼這件事重要」。寫不出來代表你有的是直覺不是決策，先把模糊處攤開。
2. **抽出最小單元** — 只留「產物」（程式碼或提案）與「契約」（它必須滿足什麼），拿掉你的推理與結論。
3. **請求對抗審查** — 提示語要求找問題，不是求認可：

   > 對抗式審查。找出這份產物的問題。假設作者過度自信。檢查：未言明的假設、未處理的邊界情況、隱藏的耦合與共用狀態、契約違反、破壞既有慣例、非預期輸入下的失效模式。不要驗證它是對的。找出問題，或明確說你找不到。

   **只給產物與契約，不給 CLAIM。** 把結論一起交出去，審查者會傾向附和。
4. **逐項分類**（依序判斷，先中者為準）：
   - **契約沒寫清楚** — 修契約，重跑一輪
   - **真實且該修** — 改產物，重跑一輪
   - **真實但取捨後接受** — 明確記錄取捨理由
   - **雜訊** — 審查者缺少你有的脈絡；記下來，並自問契約是否該把它擋掉
5. **停止** — 只剩瑣碎或重複發現時停；滿三輪仍有實質問題就**升級給使用者**，不要自己跑第四輪。三輪未收斂本身就是「這東西還沒準備好」的訊號。

### 與既有機制的關係

- TDD 的 **Red 步驟就是對行為宣稱的具體化懷疑**——已寫出失敗測試的行為宣稱，本節不必再跑一輪。
- `.spectra.yaml` 的 `audit: true` 只涵蓋安全面向（危險預設值、型別混淆、靜默失敗）；本節涵蓋的是一般性決策。
- 與 spec 或既有決策衝突時，依既有紀律**停止並回報**，不自行選邊。

### 反模式

- 對改名、格式化這種操作跑對抗審查
- 拿到審查結果不重讀產物就照單全收
- 問審查者「這樣好嗎」而不是「找出問題」
- **審查表演**：連續兩輪以上審查者提出實質發現，卻沒有任何一項被判定為該修——這是在自我驗證，不是在懷疑，升級處理
- 產物沒改就重跑審查（會得到相同發現，那是拖延）

## 2. 介面與契約設計

**適用條件**：本次工作涉及對外 API、跨模組介面，或會被其他程式消費的資料結構。純內部實作細節不適用。

- **契約先行。** 實作前先定義輸入、輸出與所有錯誤情況；型別定義本身就是文件。
- **錯誤語意全域一致。** 選定一種策略後全面套用：結構化錯誤體，含機器可讀的 code 與人可讀的訊息。不要有些拋例外、有些回傳 null、有些回傳錯誤物件。
- **只在邊界驗證。** 驗證發生在外部輸入進入系統之處：route handler、表單處理、第三方回應解析（一律視為不可信）、環境變數載入。共用型別契約的內部函式之間不重複驗證。
- **加而不改。** 以新增可選欄位擴充介面，不移除或改變既有欄位的型別與語意。
- **命名可預測。** 資源用複數名詞、不放動詞；欄位命名慣例全專案一致；布林值用 is/has/can 前綴。
- **列表端點一開始就支援分頁。** 「現在資料量還小」不是理由。

**Hyrum's Law**：只要使用者夠多，系統所有可觀察的行為都會被某人依賴，無論契約怎麼寫。所以要刻意決定哪些行為對外暴露，不要洩漏實作細節，並在設計當下就想好汰除路徑。

**單一版本原則**：以擴充取代分版本。同時維護多版本會讓成本翻倍並製造相依問題。

## 3. 可觀測性

**適用條件**：本次工作涉及會長期執行的服務、排程作業或外部系統整合。一次性腳本與純函式庫不適用。

### 先寫問題，再加訊號

動手加任何遙測之前，先寫下值班的人會問的 2–4 個具體問題。**每一個訊號都要對應到其中一題**；對應不到就不要加。

```
功能：付款重試
值班會問：
1. 有多少比例是第一次就成功，多少是重試後才成功？
2. 永久失敗時，原因是什麼？（供應商錯誤／逾時／驗證失敗）
3. 供應商是不是比平常慢？
```

### 結構化 log

- 用**欄位**，不要字串插值。`log.Warn(new { evt = "payment_failed", provider, errorCode, attempt })` 而不是 `log.Warn($"付款 {id} 失敗，重試 {n} 次")`——後者無法篩選、無法聚合、無法告警。
- **correlation ID 在入口產生或接收**，貫穿所有 log、span 與對外呼叫，並回寫到回應標頭。沒有它，每一行 log 都是孤兒。
- 層級語意固定：`error`＝不變條件被打破、`warn`＝降級但已處理、`info`＝重要業務事件、`debug`＝正式環境預設關閉。
- **絕不記錄密碼、token、金鑰或未遮蔽個資**，也不要記整個 request body——採欄位白名單。這與專案既有的機密界線一致，不因除錯需要而放寬。

### 指標

- 每個端點與每個外部相依都做 **RED**：Rate（每秒請求數）、Errors（失敗率）、Duration（延遲分布）。佇列與連線池另做 USE：使用率、飽和度、錯誤數。
- **延遲用 histogram，查 p95/p99，不用平均。** 平均值會蓋掉那 1% 體驗極差的使用者。
- **label 只能是有界集合**：路由樣板、狀態類別（`5xx` 而非 `500`）、供應商名稱。**user ID、request ID、完整 URL、錯誤訊息文字絕不可當 label**——它們會讓時序數量爆炸並拖垮後端。這類高基數查詢屬於 log 與 trace。

### 告警

- **只對症狀告警**（使用者受影響：錯誤率、延遲、佇列積壓時間），成因（CPU、記憶體、重啟）只放儀表板。對成因告警會在沒事時響、在沒預料到的失效時沉默。
- 每個告警必須：**可行動**（回應是「不用管，會自己好」就刪掉它）、**附處理步驟**（這代表什麼、先查什麼、找誰）、**門檻有依據**（來自 SLO 或歷史資料，不是猜的）。
- 只用兩級：**立即處理**（使用者受影響）與**本週處理**（降級）。三級以上會被當成雜訊忽略。

### 驗收

在測試環境**故意觸發一次失敗，只靠遙測就能定位問題**——不看原始碼。做不到就表示遙測還沒完成。

## 4. 以官方文件為準

**適用條件**：本次工作用到框架、函式庫或平台 API。純專案內部邏輯不適用。

流程固定四步：**定版本 → 抓文件 → 照做 → 標出處**。

### 先定版本

從相依檔案讀出確切版本並明講出來——`package.json`、`*.csproj`、`pyproject.toml`、`requirements.txt`、`go.mod`、`Cargo.toml`、`Gemfile`。

```
偵測到：
- .NET 8.0（來源：ScheduleTools/QuartzTemplate.csproj）
- Quartz.NET 3.8.1（來源：同上）
→ 取這兩個版本的官方文件。
```

**版本不明就問，不要猜。** 同一個 API 在相鄰版本簽章不同是常態。

### 抓文件

取該功能的**具體文件頁**，不是首頁、不是關鍵字搜尋結果。有 context7 之類的文件 MCP 就用它，否則直接抓官方文件 URL。

來源權威順序：

| 順位 | 來源 |
|---|---|
| 1 | 官方文件 |
| 2 | 官方 blog／changelog／遷移指南 |
| 3 | 網頁標準與規格書（MDN、規格原文） |
| 4 | 相容性資料 |

**不可當作主要依據**：Stack Overflow 回答、部落格、教學文、AI 生成的文件，以及自己的訓練資料。它們可以當線索，但結論要回到官方來源確認。

### 照文件實作

用文件上的簽章，不用記憶中的簽章。文件推薦新做法就採用新做法；遷移指南標為 deprecated 的寫法不要用。

**文件與既有程式衝突時攤開問**：

```
衝突：既有程式用 X，但 <版本> 的官方文件建議 Y。
A) 照文件用 Y —— 與目前文件一致
B) 照既有程式用 X —— 與 codebase 一致
請選擇。
```

不要默默選邊——攤開問的完整格式見第 5 節。

### 標出處

非顯而易見的框架決策要留下完整 URL（能深連結到錨點更好），程式碼註解與回覆各留一份。

**查不到就明說未驗證**：

```
未驗證：找不到這個用法的官方文件，以下依訓練資料撰寫，可能已過時，上線前請確認。
```

「這可能有點舊」這種模糊免責是最糟的選項——要嘛查證並附出處，要嘛明確標為未驗證。

## 5. 升級給人的格式與迴圈上限

**適用條件**：本檔任一節、或專案任一條紀律要求「停止並回報」「升級給使用者」時。同一個問題反覆修不好時也適用。

前四節與專案其他紀律都會在某些情況要求停下來問人，但多半只說「停止並回報」，沒說要回報什麼。本節補上格式，並給出「該停了」的客觀門檻。

### 升級時必給的四件事

「我卡住了，你覺得呢？」不算升級——它把整理問題的工作也一起丟回給人。合格的升級一次給齊：

1. **卡在哪** — 哪一步、觸發了哪一條紀律。
2. **試過什麼** — 已經做過的嘗試，以及各自為什麼不通。沒試過就直說沒試過。
3. **具體選項** — `A) / B) / C)`，每項寫清楚代價，並標出建議選項與理由。
4. **不決定的後果** — 這件事懸著會擋住什麼。

### 明確指定回答形式

在問題末尾指明你要的答案長什麼樣，對方才知道要花多少力氣回你：

| 形式 | 用在 |
|---|---|
| 是非 | 只有做或不做兩種走法 |
| 多選 | 已窮舉出有限選項（**預設用這個**） |
| 自由描述 | 連選項都列不出來——這通常表示前面的整理還沒做完 |

格式範例見第 4 節「文件與既有程式衝突時攤開問」。

### 迴圈上限：同一個問題三次

**同一個失敗連續嘗試三次仍未解決，停止並升級。** 這與第 1 節「對抗審查三輪未收斂就升級」是同一個門檻，理由也一樣：三次沒過本身就是訊號，代表對問題的理解有缺口，不是手法不夠花俏。

計數規則：解決後歸零；換成另一個不同的問題重新起算；**改個寫法再試一次算一次，不算重新開始**。

反模式——以下都是在繞過門檻，不是在解決問題：

- 換一種寫法再試，反覆迴圈
- 加 `try`／`catch` 讓錯誤消失
- 放寬或註解掉擋路的測試
- 「先跳過這個，之後再回來」——之後不會回來

## 6. Context 工程

**適用條件**：在大型或不熟悉的 codebase 上工作。範圍已知、只碰少數幾個檔案的修改不適用。

Context 是決定產出品質的主要變數，而且它是有限的。以下三條講的是**怎麼工作**，不是怎麼寫程式。

### 探索交給唯讀 subagent

大範圍搜尋（跨目錄 grep、掃命名慣例、找出所有呼叫點）交給唯讀 Agent，只把**結論**帶回主線程：相關檔案路徑、資訊流向、可能成因。

理由是主線程的 context 一旦被搜尋雜訊塞滿，之後所有判斷的品質都會下降——而讀過卻用不上的檔案內容，正是雜訊最大的來源。

回報形式的要求與交接給人時相同：結構化、附檔案路徑、不貼大段原始碼。

治理面的規則（誰擁有什麼、哪些 Agent 可以平行、主代理必須回讀 diff）見 `AGENTS.md` 的跨 Agent 治理節，本節不重複。

### 主動壓縮，不要等自動壓縮

每完成一個**可驗證的階段**就把狀態壓回產物再繼續——進度回任務清單、測試證據回證據檔、長期決策回 ADR。長工作在階段之間以乾淨的 context 重新開始。

把這件事留給宿主的自動壓縮是最差的做法：它在 context 已經滿了、也就是判斷力最差的時候才觸發，而且由它決定丟掉什麼。

### 人的注意力放在前面

一行錯的設計會長出數百行錯的程式；一行錯的前期理解會長出數千行。所以審查順序是**先讀理解與計畫，再讀程式**，不是逐行掃 diff。

同理，整理 context 時的取捨順序固定為：

**正確性 > 完整性 > 精簡度。**

錯的資訊最糟，缺的資訊次之，多餘的資訊只是浪費。寧可留著看似冗餘但正確的脈絡，也不要為了精簡砍掉關鍵條件。
