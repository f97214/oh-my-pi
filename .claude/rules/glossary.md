# 專案詞彙表（CONTEXT.md）

`CONTEXT.md` 是這個專案的領域詞彙表：每個術語一個 canonical term、一到兩句定義，以及應避免的同義講法。它不是 spec、不是草稿區，也不存放實作決策。

多重 context 的 repo 以根目錄 `CONTEXT-MAP.md` 列出各 context 的位置；此時先判斷目前工作屬於哪個 context，不確定就問。

## 開工前必讀

1. 建立提案或開始實作前，先讀 `CONTEXT.md`（存在 `CONTEXT-MAP.md` 時改由它找出對應 context 的詞彙表）。
2. 兩者皆不存在時本節不適用；不要為此建立空詞彙表。

## 實作時

- 型別、函式、變數、資料庫欄位與 spec 用語一律沿用 canonical term。
- 詞彙表列在 `_避免_` 底下的講法**不得出現在新程式碼與新文件**。
- 需要一個詞彙表沒有的領域概念時，先敲定術語再寫程式——不要先寫了再回頭補定義。

## 衝突停止

使用者用語、程式碼現況與詞彙表定義三者互相矛盾時：**停止並回報**，由使用者決定要修訂詞彙表還是改用既有術語。不得自行選邊，也不得默默引入同義詞。

範例：詞彙表把「取消」定義為整張訂單作廢，但需求描述像是部分取消——這是兩個不同的概念，攤開來問，不要猜。

## 詞彙表共用契約

## 結構

```md
## Language

**Order**：
客戶送出、由本系統承接履行的採購請求。
_避免_：Purchase、transaction
```

- **要有立場。** 同一個概念有多個講法時，選定最好的那一個，其餘列在 `_避免_` 底下。
- **定義要緊。** 最多一到兩句。定義它「是什麼」，不是它「做什麼」。
- **只收錄專屬於這個專案 context 的術語。** 一般程式概念（timeout、錯誤型別、utility 模式）即使專案大量使用也不該收。加詞之前先問：這是這個 context 獨有的概念，還是一般程式概念？只有前者才能進。
- **出現自然的群聚時用子標題分組。** 若所有術語屬於同一個緊密領域，平鋪列表即可。

術語一敲定，**當場**依共用契約寫入詞彙表，不累積到最後批次處理。
