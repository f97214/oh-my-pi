# Grill：需求訪談＋領域建模

釐清影響方案與驗收的重要問題，直到雙方足以做出決策。把整個設計視為一棵**決策樹**：每個決策底下掛著依賴它的後續決策。

## 訪談協議

以決策的依賴關係分輪提問；只問會改變範圍、方案、限制或驗收的問題。已回答的決策沿用，不重問。將能獨立回答的問題合併成容易處理的一輪，附建議與取捨；依賴尚未決定事項的問題留到下一輪。

宿主有提問工具時使用工具，否則可使用以下格式：

```
❓ **Q1** - **<問題標題>**：<問題與選項>

➡️ <建議答案與取捨>
```

環境事實先自行查證；有可用子代理且工作可獨立驗證、值得分工時才委派。缺少子代理不妨礙自行探索；等待探索時可繼續不相依問題。

目標、範圍、重大取捨與驗收足以支持下一步時結束訪談，列明已確認結論及仍有影響的假設。不要為了走遍所有分支繼續提問。本 skill 維持訪談與文件沉澱用途，不因達成共識自行開始應用程式實作。

## 訪談中同步進行領域建模

訪談不只是問答，也要主動打磨專案的領域模型。過程中隨時執行以下紀律：

### 對照詞彙表提出質疑

使用者用了與 `CONTEXT.md` 現有定義衝突的詞時，立即指出：「詞彙表把『取消』定義為 X，但你現在的意思像是 Y——是哪一個？」

### 收斂模糊用語

使用者用了含糊或多義的詞時，提議精確的 canonical term：「你說『帳號』——指的是 Customer 還是 User？這是兩個不同的東西。」

### 用具體情境戳邊界

討論領域關係時，發明會踩到邊界的具體情境來壓力測試，逼出概念之間的精確分界。

### 與程式碼交叉比對

使用者陳述系統行為時，檢查程式碼是否同意。發現矛盾就攤開來：「程式碼是整張訂單取消，但你剛說可以部分取消——哪個才對？」

### 即時更新 CONTEXT.md

術語一敲定，**當場**寫入專案根目錄的 `CONTEXT.md`，不要累積到最後才批次處理。格式見 [CONTEXT-FORMAT.md](./CONTEXT-FORMAT.md)。

`CONTEXT.md` 必須完全不含實作細節。它不是 spec、不是草稿區、不是實作決策的存放處——它是詞彙表，僅此而已。

### 節制地提議 ADR

只有以下三個條件**全部**成立才提議建立 ADR：

1. **難以回頭**——之後改變主意的成本很可觀
2. **沒脈絡會困惑**——未來的讀者看到程式碼會納悶「當初到底為什麼這樣做？」
3. **真實取捨的結果**——確實有其他選項，而你基於特定理由選了這個

缺任何一項就跳過。格式、索引與 supersede 程序見 [ADR-FORMAT.md](./ADR-FORMAT.md)。檔案採 lazy 建立：`CONTEXT.md` 在第一個術語敲定時才建，`docs/adr/` 在第一份 ADR 需要時才建。

ADR 建立後**當場**更新 `docs/adr/README.md` 索引；與既有 `accepted` ADR 衝突時停下來，由使用者決定是修訂目前的想法，還是以新 ADR supersede 舊決策——不要默默推翻。

## 與 Spectra 的銜接

- 訪談達成共識後的結論，可直接作為 `/spectra-propose` 的需求輸入；訪談中確立的檔案路徑與範圍可餵給 proposal 的 Impact 區段。
- 本 skill **絕不**寫應用程式碼、**絕不**建立 Spectra change——那是 `/spectra-propose` 之後的事。訪談結束時，若適合，提示使用者可執行 `/spectra-propose` 進入正式流程。
