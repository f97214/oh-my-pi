# 第一性原理拆解

不從「別人怎麼做」出發，而是拆到不能再拆的地基事實，再由下往上重建。

## 與其他 skill 的分工

| Skill | 對象 | 問題 |
|---|---|---|
| `/grill` | **人** | 你到底想要什麼？隱含假設是什麼？ |
| **本 skill** | **問題本身** | 這個需求該存在嗎？哪些「限制」是真的？ |
| `.claude/rules/engineering.md` 的對抗審查 | **已成形的產物** | 這個做法哪裡會壞？ |

三者角度不同，可接續使用：先拆問題，再訪談人，最後審查產物。

## 何時使用

- 評估架構或設計是否真的最佳
- 質疑「最佳實務」在當前脈絡是否適用
- 慣例解法都不夠好、需要突破時
- 影響長遠的基礎決策
- 挑戰遺留系統裡繼承來的假設
- **懷疑某個需求或步驟根本不該存在**

不適用：已經清楚的小改動、機械性操作、使用者已明確指定做法且無重大風險時。不要對每個決策都跑一遍——留給重要的選擇。

## 階段 0：先試著刪掉它

**這是最容易被跳過、也最有價值的一步。** 在優化任何東西之前，先問它該不該存在。

1. 試著整個刪掉——沒有這個步驟／功能／限制，系統還能運作嗎？
2. 刪得掉就刪掉。不要優化一個本來就該消失的東西。
3. 刪不掉，再加回來，然後才開始分析。
4. 追問這個需求是誰提的——**聰明人提的需求最危險**，因為沒人會質疑。

需求可能不該存在的訊號：

- 「我們一直都有這一步」
- 「法規要求」（去查證——常常是過時的理解）
- 「使用者期待這樣」（最近一次問使用者是什麼時候？）
- 「規格書上寫的」（誰寫的、為什麼寫？）

## 階段 1：問題的本質

1. 把問題講清楚——到底要解決什麼？
2. 分開症狀與成因——這是真正的問題，還是某個問題的表現？
3. 定義成功條件——完美的解法會達成什麼？

問自己：這裡真正要完成的工作是什麼？如果這個系統不存在，使用者實際上需要什麼？撇開做法不談，哪個結果才重要？

## 階段 2：挑戰所有假設

先列出明講的假設，再挖出沒明講的——那些「大家都這樣做」而從未被檢視的慣例。

| 類別 | 該問的問題 |
|---|---|
| 技術 | 一定要用這個技術／模式嗎？ |
| 業務 | 這個需求真的是固定的嗎？ |
| 資源 | 這些限制是真實存在還是想像的？ |
| 歷史 | 當初為什麼這樣決定？條件還在嗎？ |

假設很可能是假的訊號：「我們一直都這樣做」「業界標準就是這樣」「大家都用 X」「這太簡單了不可能行」。

## 階段 3：確立地基事實

哪些東西不可違反——物理與數學的限制、業務上必須恆真的不變量、使用者根本上的需要。

一項陳述要當地基事實，必須通過三個檢驗：**還能再拆嗎？可以證明為真，而不只是普遍相信？違反它一定會失敗嗎？**

## 階段 4：由下而上重建

1. 從最小開始——滿足地基事實的最簡形式是什麼？
2. 只加必要的——每一項增加都要自己說明理由。
3. 逐層挑戰——這一層值得它帶來的複雜度嗎？

```
地基事實 → 最小解 → 有理由的增補 → 最終設計
 （可證）   （夠用）    （逐項辯護）
```

## 階段 5：驗證推理鏈

- 每個設計決策都能回溯到某項地基事實嗎？
- 推理鏈哪一段還踩在假設上？
- 什麼情況會讓這個方案垮掉？

## 三個常見陷阱

| 陷阱 | 症狀 | 檢驗方式 |
|---|---|---|
| 複雜度 | 解法的規模超過問題本身 | 拿掉一個元件——系統還能解決核心問題的話，那個元件就不是必要的 |
| 類比 | 「某某公司都這樣做」 | 我們的問題在所有相關維度上都跟他們一樣嗎？哪些限制不同？ |
| 遺留 | 為了相容早已無人使用的東西 | 當初的條件還在嗎？真正的改變成本與持續維護成本，哪個大？ |

## 輸出格式

```markdown
## 第一性原理分析：{主題}

### 0. 需求檢驗（先試刪除）
嘗試刪除：{做了什麼嘗試}
結果：{已刪除／無法刪除，因為……}

### 1. 問題本質
核心問題：{一句話}
成功條件：{可衡量的結果}

### 2. 被挑戰的假設
| 假設 | 為何質疑 | 結論 |
|---|---|---|
| … | … | 保留／捨棄／修改 |

### 3. 地基事實
- {不可再拆的事實}

### 4. 推理鏈
地基事實 → {步驟} → {步驟} → 方案

### 5. 結論
建議做法：{描述}
關鍵洞察：{發現了什麼}
接受的取捨：{放棄了什麼}
```

## 邊界

**會做**：有系統地挑戰假設、找出地基事實、從根本建立推理鏈、指出慣例在此不適用之處、質疑需求該不該存在。

**不會做**：把既有方案一律當成錯的、對每個決策無限投入時間、為了理論純粹而無視現實限制、保證找到「最好」的答案——它給的是更好的推理，不是完美解。

## 領域知識不足時

對這個領域了解太少，連該問什麼都不確定時，先別急著拆解。用四象限盤點一輪：**已知的已知**（確定的事實）、**已知的未知**（知道自己不知道，可以去查）、**未知的已知**（團隊裡有人知道但沒說出來的默會知識）、**未知的未知**（連問題都問不出來的盲區——靠找相鄰領域的人聊、讀事故報告、看競品失敗案例來逼出）。盤完再回到階段 0。

## 檢查清單

- [ ] 需求試過刪除，確認不能整個拿掉
- [ ] 問題以「結果」而非「做法」陳述
- [ ] 假設全部列出並逐一挑戰
- [ ] 地基事實通過三項檢驗
- [ ] 方案完全由地基事實往上建
- [ ] 每個設計決策都能回溯到某項地基事實
