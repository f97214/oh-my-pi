# 特殊弱點處理與嚴重度



這兩類弱點的「修補」不只是改程式碼,漏掉後半段等於沒修:

**硬編碼祕密**——祕密只要進過版控就**視同已外洩**,修補要做三件事:

1. 程式改為從環境變數、User Secrets 或祕密管理服務(如 Key Vault)讀取。
2. **提醒使用者輪替(rotate)該祕密**——舊值已外洩,只改讀取方式擋不住已經拿到它的人。
3. 提醒 git 歷史仍留有舊值,可用 `git filter-repo` 或 BFG 清理——這會改寫歷史、影響所有協作者,**屬使用者決策,不要代為執行**。

**套件 CVE / 依賴弱點**——依序確認,不要看到 CVE 就升版:

1. 從 lockfile / `*.csproj` / `requirements.txt` 確認**實際安裝版本**真的落在受影響區間。
2. 確認**受影響的 API 是否真的被本專案呼叫**;沒呼叫到就如實標註「暫不可利用、急迫性低」,仍建議排程升級。
3. 優先升級到**官方修補版**,通常是最小且最穩的解。
4. 無法升級(相依鎖死、EOL)時,給暫時緩解(如在邊界擋輸入),並**明說這不是根治**。
5. 升級前檢查 changelog 的 breaking changes,把相容性風險寫進修改計畫。

## 弱點清單與嚴重度

需留意並避免在修補中引入的弱點(附 CWE 編號,方便對照 SAST 報告):

SQL Injection(CWE-89)、Command Injection(CWE-78)、Path Traversal(CWE-22)、XSS(CWE-79)、SSRF(CWE-918)、不安全反序列化(CWE-502)、認證繞過(CWE-287)、授權繞過/Broken Access Control(CWE-284/862)、硬編碼祕密(CWE-798)、Race Condition(CWE-362)、不安全亂數(CWE-330)、敏感資料外洩(CWE-200)、過度詳盡的錯誤訊息(CWE-209)、不安全檔案上傳(CWE-434)、Open Redirect(CWE-601)、Prototype Pollution(CWE-1321)、Regex DoS/ReDoS(CWE-1333)。

**嚴重度分級**(用於排序與溝通):

| 嚴重度 | 判定條件 | 範例 |
| --- | --- | --- |
| Critical | 未認證可直接利用,或造成 RCE/資料外洩 | 可控輸入直達 `eval`;字串拼接 SQL 對外開放 |
| High | 需常見前提即可利用,影響重大 | 已登入即可越權讀他人資料;反序列化不可信輸入 |
| Medium | 需特定條件或互動才可利用 | 反射型 XSS 需誘導點擊;SSRF 受網路分段限制 |
| Low | 需刻意誤用或影響有限 | 偵錯訊息洩漏少量內部路徑 |
